# Спецификация требований (этап «Анализ требований»)

**Заказчик:** подразделение финансово-экономического блока университета (финансовый
мониторинг задолженности обучающихся по договорам об оказании платных образовательных услуг).
**Исполнитель:** команда разработки, место практики — ИТ-подразделение университета.

## 1. Контекст и проблема
Сейчас контроль задолженности ведётся вручную в таблицах: сложно оперативно видеть
просрочку, автоматически начислять договорные пени и принимать решения о рассрочке.
Требуется модуль, который считает график, долг, пени и рейтинг платёжной дисциплины.

## 2. Функциональные требования
| ID | Требование | Проверка |
|---|---|---|
| FR-1 | Загрузка договоров и платежей из CSV | тест загрузки, валидация дат |
| FR-2 | Формирование помесячного графика платежей (10 платежей за учебный год) с учётом скидки | сумма графика = сумма к оплате |
| FR-3 | Распределение поступлений по графику (FIFO) и расчёт остатка долга | тест «полностью оплаченный договор» |
| FR-4 | Расчёт просроченной задолженности, пени (1/300 ключевой ставки ЦБ РФ за день) и возрастных корзин (1-30/31-60/61-90/>90) | контрольный расчёт пени |
| FR-5 | Рейтинг платёжной дисциплины 0-100 и решение по рассрочке | монотонность и границы шкалы |
| FR-6 | Обезличивание ФИО и маскирование номеров платёжных карт в отчётах | тест маскирования |
| FR-7 | Сводка портфеля: сбор платежей, доля дебиторов, IRR рассрочки | тест NPV/IRR |
| FR-8 | Претензионная очередь, отсортированная по сумме к взысканию | тест сортировки |
| FR-9 | Журнал операций с hash-цепочкой и проверкой целостности | тест подмены записи |

## 3. Нефункциональные требования
| ID | Требование |
|---|---|
| NFR-1 | Производительность: расчёт портфеля из 50 000 договоров не более 10 с (батч-обработка) |
| NFR-2 | Доступность не ниже 99,5 % в период приёмной кампании и сессий |
| NFR-3 | Масштабируемость: добавление филиалов без изменения кода (конфиг, а не правка) |
| NFR-4 | Объяснимость: каждое решение скоринга раскладывается на весовые слагаемые |
| NFR-5 | Безопасность: пароли — PBKDF2-HMAC-SHA256 (200 000 итераций), права RBAC, TLS 1.3 в контуре API |
| NFR-6 | Аудит: неизменяемый журнал действий с контролем целостности |
| NFR-7 | Переносимость: только стандартная библиотека, Python 3.10+, без привязки к ОС |
| NFR-8 | Покрытие юнит-тестами ключевых расчётов — не ниже 85 % |

## 4. Требования по безопасности и соответствие регулированию
* **152-ФЗ «О персональных данных»** — обезличивание ФИО в массовых отчётах, разделение
  прав «авторизованный/аналитик», хранение идентификаторов субъекта отдельно от расчётных данных.
* **115-ФЗ / 273-ФЗ** — фиксация подозрительных операций (нетипичные суммы, дробление платежей)
  в журнале; на учебном этапе реализован только аудит-лог.
* **ГОСТ Р 57580 (рекомендации Банка России по безопасности финансовых операций)** —
  двухфакторная аутентификация и полиция сложности паролей как базовый уровень.
* **Условия договора оферты вуза** — размер пени берётся из договорной формулы 1/300 ключевой ставки,
  ставка параметризуется (не «зашивается» в код).
* Порядок «три уровня доступа к данным» (студент / куратор / бухгалтерия) закладывается в RBAC-матрицу.

## 5. Ограничения и допущения
* Данные-источник — выгрузки из 1С и LMS в формате CSV (в продуктиве — интеграции по API).
* Учебный вариант использует синтетические данные; реальные ПДн не обрабатываются.

## 6. Критерии приёмки
1. `python -m unittest discover -s tests` — все тесты зелёные.
2. `python -m src.cli report` формирует CSV-отчёт с колонками долга, пени и рейтинга.
3. Сумма графика равна сумме к оплате; полностью оплаченный договор даёт нулевую просрочку.
4. В отчёте ФИО обезличены, а журнал операций проходит проверку целостности.
